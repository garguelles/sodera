# ENSv2 onboarding and annual renewal

Status: namespace deployed and mounted on current Sepolia ENSv2; user-name issuance, renewal, and onboarding are not yet implemented.

## Product decision

Give each wallet user one real `<username>.sodera.eth` identity on the **current Ethereum Sepolia ENSv2 beta deployment**. The name is an ENSv2 ERC1155Singleton token owned by the user's passkey-controlled Kernel smart account. Deploy a standard ENS `PermissionedResolver` for that Kernel, granting record and resolver authority only to it. A Sodera-owned resolver-only alias does not meet this ownership requirement. The historical ETHOnline deployment in [PRA-206](../research/PRA-206-ensv2-namespace.md) is not the current hierarchy.

New names last one year and have a **zero Sodera registration price**. Renewal has a **zero Sodera price** too; Sepolia gas still applies. Open renewal during the last 90 days of the current term and extend its expiry by one year. A renewal path callable by anyone holds only root `ROLE_RENEW`, permits self-funded gas, and can offer bounded sponsorship. Reject renewal of unregistered/expired names through this public path, extensions beyond the parent's expiry, and repeated early extensions. Renew `sodera.eth` before its remaining lifetime would block a child issuance or renewal. ENSv2 has no automatic grace period: expiry immediately interrupts identity and an expired label can be registered by someone else. No automatic renewal or permanently free gas is promised.

The owner controls `0x7Ed08e45067d7Bb1c064055eC99aCD6586453915`. They deployed and mounted child registry `0xfBb4ef18Db7F8044a0A19fD1Db7B192327811EC7` on Sepolia; [independent receipt and state checks](../research/ensv2-sepolia-namespace-check.md#mounted-child-registry) confirmed the factory implementation, canonical parent, pointer, and initial roles. The app still displays only a fixture name; no issuer or renewer has been authorized. ENS warns that its Sepolia beta state may be reset periodically; deployment addresses and name state must be revalidated before a release or demo.

## Architecture and trust boundaries

- Deploy one standard `UserRegistry` proxy via the current ENS Verifiable Factory. Set its canonical parent to the current `.eth` registry and mount it under `sodera.eth`. Pin the deployed factory, implementations, ABIs, Universal Resolver, initializer calldata, and role bitmap from current sources. Do not reuse ETHOnline addresses.
- An authenticated, operator-controlled issuer holds **only** root `ROLE_REGISTRAR`. It enforces username policy, one active Sodera name per Kernel *in the product*, abuse limits, request serialization, idempotency and a global issuance budget. These are service rules, not on-chain personhood or transfer restrictions. No issuer/private key belongs in the mobile app or static landing site.
- For each claim, deploy an official factory resolver proxy with only the Kernel as grant recipient and set coin type `60` for the full DNS-encoded name to the same Kernel. Register with zero child-registry pointer and the exact name-scoped owner bitmap in [ADR-0011](../adr/0011-ensv2-user-subnames.md). Do not give the issuer resolver rights or ERC-1155 operator approval.
- A small, reviewed renewal contract holds only root `ROLE_RENEW`, checks registered state, the 90-day window, one-year extension and parent expiry on chain, and requires no name price. Anyone may pay gas to call it. Limit sponsored renewal independently through the existing sponsorship service; do not put a sponsor credential in client code.
- After a controlled end-to-end claim, verify registry provenance, child root roles and unauthorized-action reverts before revoking dangerous child root roles and locking its canonical-parent pointer. The `sodera.eth` ancestor can redirect the subtree until its name-scoped subregistry pointer authority and all other effective holders/operators are removed. Ask the parent owner to review and explicitly approve that **irreversible** step separately; never describe identities as fully emancipated based only on `UserRegistry.isEmancipated()`.

## Implementation order

1. **Read-only deployment gate.** Verify chain ID `11155111`, the parent's current `REGISTERED` state/owner/expiry, `.eth` and root pointers, operator/role holders, implementation provenance and ENSv2 Universal Resolver behavior. Record evidence and exact addresses separately from application defaults. Stop if ownership or canonical traversal disagrees with the user's expectation.
2. **Claim-authentication proof.** Confirm a deployed Kernel can authenticate a short-lived, single-use server challenge with the pinned ZeroDev passkey path and that the service can verify it against that Kernel. Do not accept a client-supplied address alone. Require the existing wallet and deployed account before opening issuance publicly.
3. **Owner-reviewed registry setup — complete.** The owner used the [standalone local MetaMask owner app](../../ens/README.md) for separate, receipt-checked transactions. The owner has only `ROLE_SET_PARENT`, `ROLE_REGISTRAR_ADMIN`, and `ROLE_RENEW_ADMIN` on the child. Retain the latter two under the owner's control to grant/revoke a registrar and renewal principal as needed; review operational key-rotation and retained admin trust before public issuance. Revoking `ROLE_SET_PARENT` after testing is a separate irreversible operation, as is locking the ancestor pointer. Do not rerun `pnpm prepare:registry` against the already mounted namespace. See [deployment evidence](../research/ensv2-sepolia-namespace-check.md#mounted-child-registry).
4. **Idempotent claim service.** Pin an ENSIP-15 normalization implementation; accept canonical ASCII labels of 3–20 characters, with letters at both ends and only letters/digits/internal hyphens. The initial proposed reserved list in `app/src/ens/username.ts` is `admin`, `anon`, `api`, `ens`, `help`, `official`, `root`, `security`, `sodera`, `support`, `wallet`, `www`; approve it before opening public claims. Validate in app and issuer using the same rules. Check exact normalized label status (`AVAILABLE`, `RESERVED`, `REGISTERED`); serialize competing claims; persist `(chain ID, child registry, labelhash, Kernel)` and transaction status. On timeout/retry, reconcile chain state before submitting again. Reject issuance past parent expiry or global budget.
5. **Resolver and ownership confirmation.** Deploy the user's factory resolver, initialize its Kernel-only grants and ETH record, register the token and resolver pointer, then verify registered state, owner, proxy provenance, current pointer, canonical traversal, and resolved coin-60 address via the current ENSv2 Universal Resolver. Only then mark the name issued.
6. **Renewal path.** Deploy/test the restricted renewal contract, authorize only that contract for root renewal, and remove unintended renewal principals. Expose renewal status and transaction review in-app. Show notices at 90, 30 and 7 days before expiry, plus explicit expired/parent-expired states. Renewing changes neither wallet ownership nor resolver records.
7. **Onboarding and identity UI.** Replace `app/src/onboarding/onboarding.ts`'s mock claim and `app/src/components/onboarding-screen.tsx`'s hardcoded `anon.sodera.eth` with choose/check/claim/pending/reconcile/confirmed states. Version persisted profiles; preserve existing wallet identities and label mock-era profiles unverified. Restore pending claims after restart without duplicating transactions. Finish onboarding as a verified ENS identity only after chain confirmation. Recover Wallet reuses the same Kernel and rechecks its name rather than issuing a second one.
8. **Product integration.** Replace the fixed name in `app/src/wallet/wallet-home-live.ts` with verified chain state. Refresh on app foreground and before identity-sensitive operations; use an address-only fallback when a name transfers, expires, loses its canonical path, or no longer resolves to the current Kernel. Audit `app/src/wallet/send-transfer.ts` so recipient reads and confirmation use the current ENSv2 Universal Resolver and bind approval to the exact resolved address. Route future avatar writes through the Kernel-authorized operation lifecycle and the name's *current* resolver.

## Verification and launch gates

- Exercise a fresh Android create-wallet → confirmed name → Home flow and an interrupted/restarted registration; confirm no duplicate issuance and no mock name presented as real.
- Prove Kernel ownership and per-account resolver authority; simulate owner-permitted and issuer-forbidden record/resolver/transfer actions. Verify factory implementation, initializer grants, proxy events and public transaction links.
- Test normal renewal, a second attempt outside the 90-day window, parent-too-short, changed ownership, expiry and self-funded fallback. Confirm a failed renewal never blocks wallet access.
- Test external transfer, loss of resolver/canonical path, and reinstall/recovery retaining the same Kernel. Verify the wallet shows an address instead of a falsely verified name.
- Run relevant TypeScript, lint, and focused authorization/idempotency tests and gather live Sepolia receipts. Recheck parent lifetime and beta deployment availability before demonstrating the feature.

## Owner actions and open deployment inputs

The owner signs only reviewed parent/registry configuration transactions, provides a server-side issuance principal and hosting/secret storage, funds owner/issuer Sepolia gas, and selects a bounded sponsorship budget. Hosting and the exact reserved-label list must be recorded before opening public claims. No private key or seed phrase is shared. The irreversible parent-pointer lock is a separate, later owner decision after an end-to-end controlled claim.
