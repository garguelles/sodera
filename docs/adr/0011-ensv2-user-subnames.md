# ADR-0011: User-owned ENSv2 subnames under sodera.eth

Status: selected architecture; the child registry and one controlled user-owned subname are live on Sepolia ENSv2. Real-name onboarding is integrated in the app and awaits fresh-device end-to-end verification; renewal is deferred until after the hackathon. See [live deployment evidence](../research/ensv2-sepolia-namespace-check.md#controlled-user-claim).

Date: 2026-09-26

## Context

The [ENS Labs subnames guide](https://ens.domains/blog/post/exploring-subnames-ensv2) distinguishes resolver-only subnames (all names controlled by one owner) from tokenized subnames (each name has its own owner, expiry, and resolver pointer). Sodera promises that each user's Kernel smart account controls its own identity. Resolver-only records under a Sodera-controlled parent cannot provide that ownership, even if they resolve to the user's address. The dedicated ETHOnline deployment examined in [PRA-206](../research/PRA-206-ensv2-namespace.md) is different from the [current ENSv2 Sepolia deployment](https://docs.ens.domains/learn/deployments/#sepolia-ensv2-beta); its registration and contract addresses cannot be reused.

The app's old `anon.sodera.eth` fixture is treated as unverified legacy data. A separately controlled device flow issued a real user-owned subname; onboarding, launcher Home and Wallet Home now use confirmed ENS ownership and resolution, pending full fresh-device flow verification. See the [implementation plan](../plans/ens-onboarding-and-renewal.md).

## Decision

1. **Tokenize user identities.** Once the intended owner verifies control of `sodera.eth` on the current ENSv2 Sepolia hierarchy, deploy one standard `UserRegistry` proxy through ENS's Verifiable Factory. Set its canonical parent to the current `.eth` registry and mount it as the `sodera` subregistry. Each `<username>.sodera.eth` is an ERC1155Singleton token owned by the user's Kernel account. Do not use resolver-only aliases, a shared custodial resolver, Durin/CCIP Read, or a custom registry/resolver for user identities. Resolver-only records remain an option for Sodera-owned utility names with no separate owner, not for user identities.
2. **Give each Kernel its own resolver.** Deploy a standard `PermissionedResolver` proxy through the factory, granting record-write, link, and upgrade authority only to that Kernel account, with no Sodera writer/admin. Initialize or write an ETH coin-type `60` address record for the full DNS-encoded name pointing to that same Kernel; the user can later write the `avatar` text record with a wallet-authorized operation. No default record or shared record link supplies a user's payment address. If a Kernel owns more than one ENS name outside this product, it may reuse its resolver; a resolver's record-key grants apply across *every* name served by that instance, not just one name.
3. **Issue with owner authority, not operator overrides.** Grant each new name's Kernel `ROLE_SET_RESOLVER`, `ROLE_SET_RESOLVER_ADMIN`, `ROLE_SET_SUBREGISTRY`, `ROLE_SET_SUBREGISTRY_ADMIN`, and `ROLE_CAN_TRANSFER_ADMIN` at registration. Use a zero initial child-registry pointer; nested subnames are a later feature. Keep no Sodera root `ROLE_SET_RESOLVER`, `ROLE_SET_SUBREGISTRY`, `ROLE_UNREGISTER`, or `ROLE_UPGRADE`, nor their admin counterparts, on the child registry. Only the issuance principal gets root `ROLE_REGISTRAR`; only the renewal path gets root `ROLE_RENEW`. Pin and inspect the exact initialization grants and owner role bitmap before any names are issued. No backend receives resolver authority or ERC-1155 operator approval.
4. **Separate public onboarding from permissionless issuance.** The first release uses an operator-controlled issuance service holding only `ROLE_REGISTRAR`, rather than copying the blog's illustrative public registrar contract. The service accepts a confirmed Kernel account and a canonical label, enforces one active Sodera name per Kernel in the product, reserved-label and eligibility policy, rate limits and a global budget, and rechecks on-chain `AVAILABLE` status immediately before registering. Issue idempotently by `(chain ID, registry address, labelhash, Kernel address)` and confirm ownership, resolver, and resolved ETH address before showing an issued identity. These are service/product limits, not claims of on-chain one-person-one-name enforcement; users may transfer names outside Sodera. Do not claim registration is complete on an API success or an unconfirmed transaction.
5. **Use free, renewable, time-bounded names.** Initial expiry is one year from registration. Claiming and renewal cost users no Sodera name fee, but on-chain gas still applies; offer bounded sponsorship and a self-funded path. Renew the parent first or stop issuance if `sodera.eth` will expire sooner. Reserve product labels through the issuer's policy; an on-chain `RESERVED` entry is optional and must not be mistaken for a user-owned name. Before release, provide a bounded, callable-by-anyone renewal path holding only root `ROLE_RENEW`: it opens in the last 90 days, extends a currently registered name by one year from its existing expiry without changing owner, resolver, or roles, and rejects earlier, repeated, expired, or parent-expiry-exceeding requests. Warn at 90, 30, and 7 days and surface post-expiry status. Do not promise permanent names or silent guaranteed renewals: on expiry resolution/ownership lapses, and a subsequent registration may supersede an expired name. Renewal cannot shorten expiry; only an authorized root renewer can revive after expiry.
6. **Lock the ownership boundary deliberately.** After mounting and verifying the child registry, its parent pointer, factory/implementation provenance, permitted-owner writes, and forbidden-operator calls, revoke child root dangerous roles and their admins and lock child `ROLE_SET_PARENT`/admin. For a claim of non-custodial user names, also revoke the `sodera.eth` owner's name-scoped `ROLE_SET_SUBREGISTRY`/admin and verify no other applicable principal or approved operator can redirect that pointer. This is irreversible; until the ancestor pointer is locked, disclose that the parent owner can redirect the entire subtree even if `UserRegistry.isEmancipated()` is true. Parent expiry/renewal and ENS root governance remain upstream dependencies. Do not present the namespace as emancipated based on the child flag alone.

**Hackathon scope update (2026-09-27):** Implementing the renewal path in decision 5 is deferred until **after the hackathon**. Current names still expire one year after registration; no renewal contract or `ROLE_RENEW` grant is live, and renewal must not be presented as available. Revisit renewal, expiry reminders, parent lifetime and the self-funded/sponsored gas path before a longer-term rollout. This supersedes decision 5's “before release” timing for the testnet hackathon build only.

## User and implementation behavior

- Normalize the full ENS name with a pinned ENSIP-15 implementation, then accept only lowercase ASCII `a-z`, digits `0-9`, and internal hyphens in labels of 3–20 characters; require a letter at each end. Reject normalized inputs that do not exactly match this product subset, product/system reserved words, and labels already `RESERVED` or `REGISTERED`. Apply the same policy in the issuance boundary, not just in the UI. Publish the exact reserved list and pinned normalization version with the implementation.
- The one-name-per-wallet rule is an onboarding rule, not a restriction on ERC-1155 transfers. A transfer moves the name's registry roles but does **not** transfer its resolver records or resolver roles. On transfer, expiry, or loss of the canonical hierarchy, stop presenting the name as the wallet's verified identity; do not silently rename the wallet or auto-reassign the name. The new owner must choose a resolver they control and set their own address record before Sodera treats that name as theirs.
- Read addresses and avatar via the current ENSv2 Universal Resolver on Sepolia; look up the name's *current* resolver before writes. Bind send confirmation to the resolved address and re-resolve at confirmation as specified by the payments flow. Key persisted identities by `(chain ID, registry address, labelhash)` or normalized full name, never by mutable token ID.
- Before any deployment, prove `sodera.eth` ownership and remaining lifetime in the current `.eth` registry, the current factory and implementation ABIs, and that default library resolution reaches the intended Universal Resolver. Publish verified addresses, initializer calldata, role counts/assignees, parent mount and lock transactions, and resolution/renewal evidence. If the parent is absent or owned elsewhere, stop: the old ETHOnline registration is not a fallback.

## Consequences

This gives each wallet transferable, owner-controlled ENSv2 identity and isolates resolver permissions at the account level, at the cost of a registry deployment, one resolver per Kernel, issuance operations, and an ongoing parent/child renewal path. A compromised registrar can issue available labels or consume a registration budget, but without override roles cannot rewrite existing names. The ENS guide's simple public registrar is an educational example, not the initial open-onboarding policy; a self-service contract can replace the issuer only after its eligibility, normalization, reservation, abuse, and renewal controls are specified and reviewed.
