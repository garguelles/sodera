# Exploring a migration from ZeroDev passkeys to JAW ID

**Status:** Investigation, not an architecture decision. Based on the repository and [JAW's React Native/Expo guide](https://docs.jaw.id/guides/react-native) as indexed in its [AI documentation](https://docs.jaw.id/llms.txt), reviewed 2026-09-26. No JAW integration, live-chain proof, or existing-wallet migration has been performed.

## The decision to make

Sodera's current wallet is a ZeroDev Kernel 0.3.3 smart account on Ethereum Sepolia (chain 11155111), with an EntryPoint 0.7 UserOperation signed by a user-controlled Android passkey through ZeroDev's released WebAuthn validator. JAW's native path instead offers a headless `@jaw.id/core` `Account` with native passkey callbacks, account creation/import, and its own account and transaction routing. This is an **account-architecture change**, not just a swap of the Android passkey library. In particular, JAW's documented EIP-7702 address-preservation path is for *EOAs*, not evidence that it can adopt an existing Kernel smart-account address.

Decide explicitly whether the goal is (A) use JAW for newly created wallets, (B) move existing Kernel wallets while retaining their addresses, or (C) move assets and identity to new JAW addresses with user authorization. Do not equate importing a passkey with importing the existing Kernel account. Existing balances and any future ENS records are bound to the old address until proven otherwise.

## What JAW documents for native apps

The [React Native/Expo guide](https://docs.jaw.id/guides/react-native) describes the **headless** `Account` class from `@jaw.id/core`. JAW's web UI, wagmi connector, and CrossPlatform (`keys.jaw.id`) mode are web-only, so the Sodera launcher would supply its own screens. The native configuration supplies `apiKey`, `chainId`, `rpId`, `rpName`, persistent `SyncStorage`, `nativeCreateFn` and `nativeGetFn`; the examples use `react-native-passkey` for both callbacks and MMKV storage. The guide calls for a `react-native-quick-crypto` polyfill loaded before the SDK, plus its native peers, and a custom Expo development build. Validate compatibility with this project's SDK/RN versions before installing packages or changing `app/package.json`'s `main` entry.

`Account.create(config, { username })` registers a passkey with JAW, derives an account address, and stores session/metadata; first transaction deploys the account. `Account.get(config)` restores a local session, `Account.get(config, credentialId)` prompts for a stored credential, and `Account.import(config)` selects a synced passkey and looks it up in JAW's registry. `sendTransaction`/`sendCalls` and `getCallStatus` provide execution and status. The guide describes an API key for JAW services, an EIP-7677 paymaster option, and native passkey signing; it does **not** establish equivalence to Sodera's current Kernel validator or independent recovery policy. JAW's [EIP-7702 upgrade guide](https://docs.jaw.id/guides/eip7702-upgrade) preserves an EOA address via delegation; it is not a migration path for an already deployed ERC-4337 Kernel account.

The native guide uses `Passkey.create`/`Passkey.get` callbacks. Evaluate whether Sodera's existing native module can satisfy the expected callback signatures and lifecycle behavior; an adapter may preserve the tested Credential Manager integration, but neither callback compatibility nor JAW acceptance of old credentials is established. The suggested MMKV integration is a new persistence layer; it does not automatically migrate SharedPreferences or survive an app uninstall without a discoverable passkey plus JAW registration.

## Investigation gates, in order

1. **Account continuity (blocking).** On a disposable Sepolia wallet, derive a JAW address from the same existing ES256 passkey and compare it to the stored Kernel address without overwriting the old manifest. Ask JAW whether its registry can enroll an existing non-JAW credential *and* whether its SDK can operate the exact existing Kernel/validator/factory. If not, require a deliberate new-address migration; do not label it account recovery. For a deployed wallet, test any proposed on-chain authority change with a transaction from its existing root and confirm the resulting address and owner state. No evidence currently shows that this is supported.
2. **Network and infrastructure.** Confirm in a pinned `@jaw.id/core` release that Sepolia (11155111) supports the chosen native account flow, deployment, its entry point, bundler, EIP-7677 sponsorship, status/receipts, and JAW registry endpoints. Confirm API-key issuance and limits. Current ZeroDev sponsorship and `pimlico_getUserOperationGasPrice` behavior should not be assumed portable.
3. **Native ceremony and dependencies.** Prototype an isolated development build with Expo SDK 57/RN 0.86.3: crypto initialization order, native dependencies, callback response format, Android `sodera.xyz` Digital Asset Links, credential selection, cancellation, backgrounding, and cold restart. Compare a JAW-registered passkey with an existing Sodera credential; test a clean install and a different device. Avoid writing over the existing `WalletIdentityManifest` during this proof.
4. **Security and UX.** Verify the exact bytes signed, origin/RP/UP/UV/credential checks, owner control (no remotely managed signing key), explicit operation review before the passkey prompt, failure/cancel behavior, replay resistance, independent receipt and on-chain owner verification, and loss-of-device recovery. JAW's synced-passkey import is useful but is not the independently enrolled recovery credential specified in ADR-0010.
5. **Transition design.** If address continuity cannot be demonstrated, define an opt-in, passkey-authorized transfer from old Kernel to new JAW address (ETH, ERC-20s and later allowances/positions), update the identity/address mapping and onboarding state only after confirmed receipts, and make rollback/partial transfer visible. Do not abandon an inaccessible old wallet or silently create a second wallet. Decide how existing users retain access to the legacy execution client during a staged rollout.

## Likely implementation work after the gates

- Add a wallet-backend/identity discriminator and versioned persistence path alongside `WalletIdentityManifest`; dispatch reopen, balance reads, operation execution and onboarding by selected account. Keep the legacy Kernel signer available until each affected wallet's transition is complete.
- Add JAW configuration and an SDK integration boundary for account create/get/import, address lookup, transaction preparation/submission and receipts. Add the API key and native dependencies only after chain, package and architecture validation. Keep service configuration separate from secret material; the client API key is not a signer.
- Either adapt `SoderaPasskey` to JAW's native callback contracts or replace its ceremony bridge with a tested native library, preserving domain binding, cancellation and registration-outcome handling. Wire persistent JAW `SyncStorage` without conflating its session with the legacy manifest.
- Update the proof/onboarding, wallet-home and eventual send flows to display the active backend/address and to enforce explicit confirmation and recovery behavior. Update `app/scripts/verify-*`, wallet tests and physical-device evidence for the new account contract rather than reusing ZeroDev validator fixtures as JAW proof.
- If migration is approved, write superseding ADRs and revise hackathon scope/specs and deployment claims before presenting JAW as the wallet authority.

## Open questions for JAW / product

- Can JAW register or import a `sodera.xyz` credential originally created outside JAW without generating a new one? What backend registry mapping and public-key proof are required?
- Can an existing deployed Kernel 0.3.3 account with ZeroDev WebAuthn root be managed by JAW while keeping its address and on-chain root policy? If not, is new-wallet onboarding plus opt-in asset transfer acceptable?
- Does JAW's native Account path support Sepolia, and which exact factory, EntryPoint, validator/owner, paymaster and deployed bytecode versions are used there?
- Is there a public API to prepare and display final transaction/UserOperation details *before* the passkey assertion and to bind approval to those details? Can the app independently verify signatures and receipts?
- How are additional passkeys enrolled, rotated and revoked, including an independently accessible recovery passkey after loss of the original device? What does the JAW registry retain, and what happens during service unavailability?
- Should Sodera retain `sodera.xyz` as RP ID and its tested Credential Manager bridge, and is iOS in scope? Who operates the JAW API key, sponsorship policy and any identity/ENS registry?
